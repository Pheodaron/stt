## Почему сетевой слой отделён от `Session`

gRPC получает типизированные protobuf-сообщения, WebSocket получает байты JSON.
Оба должны прийти к одному действию: `session.Transcribe(ctx, data, unbuffered)`.
Сетевой код переводит запросы, результаты и ошибки между двумя представлениями.

Такой объект называют адаптером. Он согласует интерфейсы, но не дублирует
выделение речи и алгоритм буфера. Иначе исправление финализации потребовалось бы
делать отдельно для каждого протокола, с риском разного поведения.

## Что задаёт protobuf

Контракт из `.proto`:

```protobuf
service Gigaam {
  rpc transcribe(stream VoiceChunk) returns (stream TranscribedText) {}
  rpc transcribe_unbuffered(VoiceChunk) returns (TranscribedText) {}
}

message VoiceChunk {
  bytes segment = 1;
}

message TranscribedText {
  optional string partial = 1;
  optional string message = 2;
}
```

`bytes` передаёт аудиоданные без самостоятельного base64-кодирования в прикладном
коде gRPC-клиента. Числа `1`, `2` — номера полей на проводе. При изменении схемы
их нельзя произвольно переиспользовать для другого смысла.

`optional` сохраняет присутствие поля. В Go это `*string`.
Метод `GetPartial()` возвращает пустую строку и для отсутствующего поля,
и для присутствующей пустой строки. Если важен сам факт наличия,
нужно проверять `response.Partial != nil`.

В `.proto` нет объявления `package`. Поэтому полные пути методов:

```text
/Gigaam/transcribe
/Gigaam/transcribe_unbuffered
```

Каталог `proto/stt/v1` и `option go_package` не добавляют `stt.v1` к сетевому
имени сервиса. Добавление protobuf-package изменило бы существующий контракт.
Отдельный тест вызывает путь строкой, чтобы проверить это независимо от генератора.

## Что находится в `gen/`

`stt.pb.go` содержит структуры сообщений, методы доступа, описание полей,
служебное состояние protobuf и регистрацию описания схемы.
`stt_grpc.pb.go` — клиент, серверный интерфейс, регистрацию и обработчики gRPC.

Их не нужно править вручную. Исходный контракт меняется в `.proto`, затем
запускается `mise run proto`. При ручном изменении сгенерированного файла
следующая генерация сотрёт правку, а другие языки не получат соответствующего контракта.

В сгенерированном коде встречаются:

- `grpc.BidiStreamingServer[VoiceChunk, TranscribedText]` — обобщённый интерфейс
  потока с конкретными типами входа и выхода; это применение параметров типов Go.
- `sync.Once` — однократная подготовка сжатого описания protobuf при обращении.
- `protoreflect` — доступ к описанию сообщения во время выполнения.
- `unsafe.StringData` и `unsafe.Slice` — внутренняя работа генератора с описанием схемы.
- проверки совместимости версий пакетов при компиляции.

Наличие `unsafe` в сгенерированном коде не означает, что приложение так же
переинтерпретирует произвольное пользовательское аудио.

## Встраивание серверного типа

```go
type GRPC struct {
    sttv1.UnimplementedGigaamServer
    Service *stt.Service
}
```

Поле без собственного имени встраивает тип. Его методы становятся доступны
у внешнего типа, если не переопределены соответствующими методами `GRPC`.
Это композиция с продвижением методов, а не наследование классов.

Сгенерированный `UnimplementedGigaamServer` даёт безопасные ответы для методов,
которые появятся в контракте, но ещё не реализованы. Его встраивают значением,
чтобы не получить nil-указатель при обращении к такому методу.

## Независимый gRPC-запрос

`TranscribeUnbuffered` создаёт временную сессию, ставит `defer session.Close()`,
вызывает `Transcribe(..., true)` и переводит ошибку в gRPC status.

Есть намеренная особенность совместимости:

```go
return &sttv1.TranscribedText{Partial: r.Message}, nil
```

Внутри сервиса независимый результат лежит в `Message`. Для старого unary API
он отправляется в `Partial`. Это не случайный обмен полями, а сохранение
уже существующего поведения клиентов.

### Пример самостоятельного Go-клиента

Пример предназначен для запуска из модуля проекта при работающем gRPC-сервере.
Он отправляет целый самостоятельно декодируемый файл длиной не больше лимита.

```go
package main

import (
    "context"
    "fmt"
    "log"
    "os"
    "time"

    sttv1 "vks-stt-v2/gen/stt/v1"
    "google.golang.org/grpc"
    "google.golang.org/grpc/credentials/insecure"
)

func main() {
    if err := runClient(); err != nil {
        log.Fatal(err)
    }
}

func runClient() error {
    if len(os.Args) != 2 {
        return fmt.Errorf("нужен путь к аудиофайлу")
    }
    data, err := os.ReadFile(os.Args[1])
    if err != nil {
        return err
    }
    conn, err := grpc.NewClient(
        "localhost:8080",
        grpc.WithTransportCredentials(insecure.NewCredentials()),
    )
    if err != nil {
        return err
    }
    defer conn.Close()

    ctx, cancel := context.WithTimeout(context.Background(), time.Minute)
    defer cancel()
    client := sttv1.NewGigaamClient(conn)
    response, err := client.TranscribeUnbuffered(ctx, &sttv1.VoiceChunk{Segment: data})
    if err != nil {
        return err
    }
    fmt.Println(response.GetPartial())
    return nil
}
```

`insecure.NewCredentials()` соответствует серверу без TLS в рассматриваемом коде.
Для внешнего доступа схему защищённого подключения нужно настраивать отдельно.
`grpc.NewClient` создаёт канал; это не обещание, что удалённый сервис уже доступен.
Ошибка соединения может проявиться при самом RPC.

## Потоковый gRPC-метод

Серверный цикл выполняет:

```text
Recv → Transcribe → Send → Recv → ...
```

Для каждого stream создаётся отдельная `Session`.
Протокол двунаправленный, но серверная обработка сообщений одной сессии
последовательная. Это сохраняет порядок звука без mutex внутри `Session`.

`Recv` с `io.EOF` означает, что клиент завершил отправку.
Сервер вызывает `Flush`, при наличии дополнительного результата отправляет его
и завершает поток. Поэтому клиенту нужен `CloseSend`, а затем чтение ответов
до `io.EOF`, а не немедленное закрытие всего соединения.

Ниже учебная функция клиента. Она читает ответы параллельно отправке:

```go
func sendChunks(ctx context.Context, client sttv1.GigaamClient, chunks [][]byte) error {
    ctx, cancel := context.WithCancel(ctx)
    defer cancel()
    stream, err := client.Transcribe(ctx)
    if err != nil {
        return err
    }
    received := make(chan error, 1)
    go func() {
        for {
            response, err := stream.Recv()
            if err == io.EOF {
                received <- nil
                return
            }
            if err != nil {
                received <- err
                return
            }
            if response.Partial != nil {
                fmt.Println("Предварительно:", *response.Partial)
            }
            if response.Message != nil {
                fmt.Println("Зафиксировано:", *response.Message)
            }
        }
    }()
    for _, data := range chunks {
        if err := stream.Send(&sttv1.VoiceChunk{Segment: data}); err != nil {
            return err
        }
    }
    if err := stream.CloseSend(); err != nil {
        return err
    }
    return <-received
}
```

Дополнительные импорты для этой функции — `io`, `context`, `fmt` и тот же `sttv1`.
Каждый элемент `chunks` должен быть самостоятельным аудиосегментом.
Родительскому контексту стоит задать общий срок. При ранней ошибке `cancel`
прерывает чтение; буфер канала позволяет горутине сообщить результат без
оставшегося получателя.

Последовательная отправка большого количества сообщений без чтения ответов может
упереться в управление потоком gRPC. Поэтому двунаправленный клиент обычно
организует отдельное чтение ответов, как в примере.

## Перевод ошибок в gRPC

| Внутренняя ошибка | Код gRPC |
|---|---|
| `context.Canceled` | `Canceled` |
| `context.DeadlineExceeded` | `DeadlineExceeded` |
| `audio.ErrLimit` | `ResourceExhausted` |
| `audio.ErrAudio` | `InvalidArgument` |
| Прочая | `Internal` |

Полная внутренняя ошибка последнего типа пишется в журнал, клиент получает
общее сообщение. Так сетевой контракт не зависит от текста ошибки C++ или FFmpeg.

## WebSocket: соединение и состояние

`WebSocket` реализует `http.Handler` методом `ServeHTTP`.
`websocket.Upgrader` переводит HTTP-соединение в WebSocket.
По умолчанию действует проверка Origin для браузерных подключений с того же хоста.
Она не является аутентификацией пользователя.

После подключения создаётся контекст от контекста сервера, функция отмены
и запись в `connections map[*websocket.Conn]context.CancelFunc`.
Map защищается `sync.Mutex`: соединения могут подключаться и отключаться
одновременно со штатной остановкой.

Сама map создаётся через `make` в `NewWebSocket`. Нулевая map допускает чтение,
но запись в неё вызвала бы panic. Mutex отвечает за совместный доступ,
а `make` — за существование пригодной для записи таблицы; это разные задачи.

`track` проверяет флаг `closed` под тем же mutex. Это закрывает гонку вида
«начали остановку, но новое соединение добавилось после обхода списка».
`release` отменяет контекст, закрывает сокет и удаляет его из map.

`readMessages` создаёт одну сессию и закрывает её через `defer` на любом выходе.
Обычный разрыв соединения освобождает ресурсы, но не отправляет финальный текст:
отправлять его по уже закрытому соединению невозможно.

## Зачем ping, pong и сроки чтения

Отдельная горутина периодически отправляет управляющий Ping.
Полученный Pong продлевает срок чтения. Обычное полученное сообщение тоже его продлевает.

```go
timeout := 2*w.PingInterval + w.Service.Timeout
```

Если управляющий Ping не удаётся отправить, соединение отменяется и закрывается.
Таймер `time.NewTicker` освобождается через `defer ticker.Stop()`.

Gorilla допускает конкурентный `WriteControl` с обычными операциями соединения.
Это не общее разрешение запускать несколько конкурентных `WriteMessage`.
Обычные ответы здесь пишет одна горутина чтения/обработки.

Транспорт устанавливает предел размера всего WebSocket-сообщения:
`base64.EncodedLen(MaxSegmentBytes) + 4096`. Дополнительные байты оставлены
для JSON-обёртки. Поэтому крупный batch не получает отдельный полный лимит
для каждого своего элемента сверх общего предела сообщения.

## JSON-RPC: структура запроса

Пример формы запроса, где строка аудио заменена пояснением:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "upload_part",
  "params": {"segment": "ЗДЕСЬ_BASE64_АУДИОФАЙЛА"}
}
```

Поддерживаются три метода:

| Метод | Действие сервиса |
|---|---|
| `upload_part` | Продолжить текущую фразу |
| `upload_part_unbuffered` | Распознать отдельную запись |
| `flush` | Завершить текущую фразу, включая отложенный хвост VAD |

Для загрузки допустим и позиционный вариант: `"params":["BASE64"]`.
Объект должен содержать ровно одно поле `segment`, массив — ровно один элемент.
Лишние поля не игнорируются.

У `flush` разрешены отсутствие `params`, пустой объект или пустой массив.
`null` и непустые параметры текущая реализация отклоняет.

## Зачем `json.RawMessage`, `any` и проверки типов

В `rpcRequest` поля `ID` и `Params` имеют тип `json.RawMessage`.
Это исходные JSON-байты части сообщения, которые можно разобрать позже.

Для параметров поздний разбор нужен потому, что их форма зависит от метода.
Для `id` полезно сохранить исходное представление: число при ответе не нужно
заново формировать из `float64`, потенциально теряя цифры большого целого.

`json.Unmarshal` в `any` даёт разные Go-типы для объекта, массива, строки и числа.
Код различает их через type switch:

```go
switch p := params.(type) {
case map[string]any:
    // Именованные параметры.
case []any:
    // Позиционные параметры.
default:
    return "", false
}
```

Это место, где динамические типы действительно нужны из-за внешнего формата.
Внутрь сервисной логики передаётся уже проверенный `[]byte`, а не `map[string]any`.

## Уведомление отличается от запроса с `id:null`

Если поле `id` отсутствует, `request.ID == nil`: метод выполняется без ответа.
Это JSON-RPC notification — уведомление.
Если в JSON явно написано `"id":null`, байты поля существуют; ответ будет с `id:null`.

Значение ID допускается строковое, числовое или `null`. Объект, массив
и логическое значение отклоняются. Проверка использует декодирование,
но сам ответ сохраняет `RawMessage` ID.

Для `flush`, от которого клиент ждёт финальный текст, нужен запрос с ID.
Если отправить уведомление, финализация выполнится, но текста в ответ не будет.

## Проверка base64

Сначала проверяется максимальная длина закодированной строки, затем вызывается
`base64.StdEncoding.Strict().DecodeString`.
Предварительная проверка не даёт выделить большой массив для очевидно
слишком длинной строки. Ограничение декодированного аудио дополнительно
проверяется в `Processor.Decode`.

Base64 нужен из-за текстового JSON. Для gRPC такой слой в прикладном контракте
не используется. Двоичные WebSocket-сообщения эта реализация не принимает
как аудиозагрузку: они получают `Invalid Request`.

## Пакет запросов JSON-RPC

`dispatchBatch` разбирает массив, выполняет элементы по очереди и собирает
только те ответы, которые должны существовать.

- Пустой batch недопустим.
- Вложенный batch недопустим и не запускается рекурсивно.
- Если все элементы — уведомления, ответа нет.
- Последовательность сохраняет порядок изменения одной сессии.

Параллельный запуск элементов batch мог бы ускорить независимые задания,
но нарушил бы смысл `upload_part`, затем `flush` в одной сессии.
Поэтому здесь выбран последовательный обход.

## Ошибки JSON-RPC

| Код | Условие |
|---:|---|
| `-32700` | Невалидный JSON |
| `-32600` | Неправильная форма запроса |
| `-32601` | Неизвестный метод |
| `-32602` | Неправильные параметры, base64 или аудио |
| `-32001` | Превышение размера или длительности |
| `-32002` | Отмена или истечение срока |
| `-32603` | Внутренняя ошибка |

В ответе `rpcResponse` либо `Result`, либо `Error`. Оба поля — указатели с
`omitempty`; конструирующие функции заполняют только нужное.

## Пример обмена WebSocket

При условии, что первые загрузки содержат речь, окно ещё не заполнено,
а пауза окончания фразы не обнаружена:

```text
Клиент: upload_part, id=1, первый аудиофайл
Сервер: result.partial = текущая гипотеза

Клиент: upload_part, id=2, второй аудиофайл
Сервер: result.partial = новая гипотеза всего окна

Клиент: flush, id=3
Сервер: result.message = финальный текст

Клиент: дождался ответа, затем закрыл соединение
```

У независимого WebSocket-запроса итог сразу находится в `result.message`.
У независимого gRPC-запроса он находится в `partial` по историческому контракту.
Обобщать имя поля между этими двумя API без проверки нельзя.

## Почему два протокола

gRPC даёт сгенерированный контракт и типизированный клиент; удобно для
межсервисного взаимодействия. WebSocket проще подключить к браузеру
и к клиентам существующего JSON-RPC API, но нужно вручную проверять сообщения
и кодировать аудио в base64.

Вместо добавления собственного TCP-протокола использованы библиотеки,
которые уже реализуют фреймы, соединения и управление обменом.
Предметная логика общая, а различия протоколов остаются в `transport`.
