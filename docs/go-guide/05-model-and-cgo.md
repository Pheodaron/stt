## Кто выполняет нейросетевые вычисления

```text
Go-сервис
    → Go API sherpa-onnx
    → C API через CGO
    → C++ sherpa-onnx: признаки и декодирование RNNT
    → ONNX Runtime: выполнение графов
    → CPU либо CUDA
```

Go-код управляет запросами, данными и ресурсами. Он не реализует свёртки,
LSTM и матричное умножение вручную.

По сравнению с вызовом отдельного сервера моделей это убирает сетевой переход
между обработкой PCM и моделью. Цена — нативные библиотеки в контейнере,
сложность сборки и то, что нативная авария может завершить весь процесс.

Внешний сервер моделей мог бы дать общее управление моделями и объединение запросов
в пакеты. Но потребовал бы отдельного развёртывания, обмена тензорами и поддержки
RNNT-декодирования. В этой версии такой сервер не используется.

## Почему три ONNX-файла

| Файл | Назначение |
|---|---|
| `encoder.onnx` | Превратить акустические признаки в представление звука |
| `decoder.onnx` | Получить представление истории уже выбранных токенов |
| `joiner.onnx` | Объединить представления и получить оценки следующего токена |
| `tokens.txt` | Связать числовые идентификаторы с текстовыми токенами |

Здесь слово «декодер» может означать разные вещи. `audio.Decoder` декодирует
аудиоформат через FFmpeg. `decoder.onnx` — нейросетевая часть RNNT.
А алгоритм `greedy_search` в sherpa выбирает последовательность токенов.

`recognizerConfig` задаёт 16 кГц, 64 признака, тип `nemo_transducer` и `greedy_search`.
Последний выбирает лучший следующий вариант на каждом шаге. Это экономный
алгоритм, но в коде нет доказательства, что он обеспечивает максимально возможную
точность среди всех способов поиска. Переход на другой поиск требует проверки
поддержки модели и качества на записях.

## Что делает `gigaam.New`

1. Повторно проверяет `Config.Validate`.
2. Для CUDA устанавливает `NVIDIA_TF32_OVERRIDE=0` и проверяет доступность CUDA.
3. Проверяет наличие непустых обычных файлов модели и словаря.
4. Создаёт канал свободных распознавателей.
5. Загружает `MODEL_WORKERS` экземпляров sherpa.
6. Каждый успешно созданный экземпляр сохраняет в `all` и помещает в канал.

Повторная проверка конфигурации нужна потому, что `New` можно вызвать
с конфигурацией, созданной не через `FromEnv`, например из теста.

Если загрузка очередного экземпляра не удалась, `m.Close()` освобождает
уже созданные экземпляры. Конструктор не оставляет частично загруженный пул.

Проверка файлов не доказывает их совместимость: это дополнительно проявляется
при создании сессий sherpa и при инференсе. Сам Go-код также не анализирует
каждый тензор, ориентируясь только на значение `MODEL_PRECISION`.

## Два списка распознавателей с разной ролью

```go
type Model struct {
    mu        sync.RWMutex
    closed    bool
    available chan *sherpa.OfflineRecognizer
    all       []*sherpa.OfflineRecognizer
    maxBytes  int
}
```

`all` хранит всё созданное, чтобы при закрытии удалить каждый нативный объект.
`available` хранит только свободные экземпляры. Пока запрос использует экземпляр,
тот отсутствует в канале, но остаётся в `all`.

Это пул ресурсов. Он не является очередью аудиозаписей: по каналу передаются
указатели на загруженные распознаватели, а не задания клиентов.

## Получить экземпляр и гарантированно вернуть

```go
var r *sherpa.OfflineRecognizer
select {
case r = <-m.available:
case <-ctx.Done():
    return "", ctx.Err()
}
defer func() { m.available <- r }()
```

Получение из канала забирает свободный экземпляр. При отсутствии свободных запрос
ждёт. При отмене контекста может выйти из ожидания.
Отложенная отправка возвращает экземпляр независимо от последующего результата.

Так два запроса не вызывают `Decode` на одном экземпляре одновременно.
Если экземпляров два, два запроса могут распознавать параллельно.

Альтернатива — mutex вокруг одного распознавателя. При одном worker это близко
по смыслу, но канал сразу поддерживает несколько экземпляров и отменяемое ожидание.
Создание нового распознавателя на каждый запрос заставляло бы снова читать веса
и строить ONNX-сессии, поэтому модель загружается заранее.

Канал не закрывается при остановке. В этой схеме после работы есть отложенные
отправки; закрытие канала раньше них вызвало бы panic. Жизненный цикл защищён
другим механизмом — `RWMutex` и `closed`.

## Зачем нужен ещё и `sync.RWMutex`

В начале содержательной обработки:

```go
m.mu.RLock()
defer m.mu.RUnlock()
if m.closed {
    return "", fmt.Errorf("model is closed")
}
```

Блокировка чтения удерживается во время ожидания экземпляра и самого распознавания.
Несколько запросов могут одновременно держать её. Но `Close` берёт блокировку
записи и ждёт, пока эти запросы закончат работу:

```go
m.mu.Lock()
defer m.mu.Unlock()
if m.closed {
    return
}
m.closed = true
```

Таким образом нативный распознаватель не удаляется, пока запрос его использует.
Повторный `Close` ничего не удаляет второй раз.

Канал отвечает на вопрос «какой экземпляр свободен?», блокировка — «можно ли
уже освобождать весь пул?». Они решают разные задачи.
Обычный `Mutex` на всё время `Transcribe` последовательно пропустил бы запросы
даже при нескольких распознавателях и свёл бы пользу пула к нулю.

Функция сначала возвращает распознаватель через более поздний `defer`, затем
снимает `RLock` через более ранний. Обратный порядок выполнения `defer` здесь
согласован с закрытием пула.

Пустой PCM возвращает пустой текст до получения блокировки. Поэтому проверка
«закрытая модель отклоняет любой вызов» была бы слишком широкой: содержательное
распознавание отклоняется, а пустой вход вообще не обращается к модели.

## Что происходит внутри одного вызова

После получения экземпляра код создаёт `sherpa.NewOfflineStream(r)`.
Это временное состояние распознавания конкретного окна PCM; оно не совпадает
с gRPC-stream и не живёт всё WebSocket-соединение.

```go
defer sherpa.DeleteOfflineStream(s)
s.AcceptWaveform(audio.SampleRate, audio.Samples(pcm))
r.Decode(s)
```

Модель загружена один раз, а временный stream создаётся на окно. Благодаря этому
соседние запросы используют общие веса, но не наследуют чужую гипотезу.

После выполнения получается `s.GetResult()`. `strings.TrimSpace(result.Text)`
удаляет пробельные символы по краям. Здесь нет самостоятельного исправления
орфографии или генерации пунктуации языковой моделью: сервис возвращает
результат выбранной GigaAM E2E RNNT.

## Ограничение отмены

Перед `Decode` и после него проверяется `ctx.Err()`.
Но сам `r.Decode(s)` — синхронный нативный вызов без переданного `context.Context`.

Пример:

```text
00:00 — начат Decode
00:01 — истёк срок запроса
00:03 — нативный Decode вернулся
00:03 — Go увидел отмену и вернул ошибку вместо результата
```

Контекст не умеет насильно остановить произвольный C++-вызов.
Запуск `Decode` в новой горутине не решил бы эту проблему: вызывающая сторона
могла бы уйти, но вычисление продолжилось бы и всё ещё использовало ресурсы.

При отменённом запросе экземпляр возвращается в пул только после завершения
его фактического использования. `Close` также может ждать долгий нативный вызов.

## `MODEL_WORKERS` и `NUM_THREADS`: числовой пример

| Настройки | Одновременные вызовы GigaAM | Слоты обработки в `Service` | Загруженные распознаватели |
|---|---:|---:|---:|
| Workers=1, Threads=2 | До 1 | 2 | 1 |
| Workers=2, Threads=2 | До 2 | 4 | 2 |
| Workers=3, Threads=1 | До 3 | 6 | 3 |

`NUM_THREADS` передаётся в `model.NumThreads` конфигурации sherpa и относится
к нативным вычислениям. Он не меняет вместимость Go-канала.

Произведение `workers * threads` полезно как грубый ориентир нагрузки, но не равно
точному числу всех потоков ОС: существуют отдельные ONNX-сессии, VAD, FFmpeg,
сетевые горутины и служебные потоки библиотек.

Дополнительные worker увеличивают память под модели. Несколько контейнеров
также создают отдельные процессы и отдельные экземпляры модели в памяти.
Общие слои образа на диске не превращаются в общий объект распознавателя.

Для одного активного клиента увеличение числа workers само по себе не ускоряет
один вызов модели. Оно даёт параллелизм между независимыми вызовами.

## Что делает собственный CGO-код

Большую часть связи Go с C++ уже предоставляет библиотека sherpa.
Собственная CGO-обёртка проекта нужна для проверки CUDA перед загрузкой модели.

Начало Linux-файла:

```go
//go:build linux

package gigaam

/*
#cgo LDFLAGS: -lonnxruntime -ldl
#include "provider_linux.h"
*/
import "C"
```

`//go:build linux` выбирает файл по целевой ОС при сборке.
Комментарий перед `import "C"` — специальная часть CGO: заголовок и параметры
линковки. `-lonnxruntime` подключает библиотеку ONNX Runtime,
`-ldl` — средства динамической загрузки Linux.

Для других ОС компилируется `provider_other.go` с условием `!linux`.
В нём функция с тем же именем возвращает понятную ошибку CUDA.
Не требуется писать `if runtime.GOOS` в каждом вызове.

## Передача буфера ошибки из C в Go

```go
var message [1024]byte
buffer := (*C.char)(unsafe.Pointer(&message[0]))
```

Go выделяет массив байтов, передаёт C-функции его адрес и размер, затем читает
текст через `C.GoString(buffer)`. `unsafe.Pointer` здесь нужен для перехода
между представлениями указателей двух языков.

Это узкая контролируемая граница: буфер не содержит Go-указателей,
используется во время синхронного вызова и не должен сохраняться C-кодом после него.
`snprintf` в C ограничивает длину записываемой строки.
Произвольное сохранение Go-указателя нативной библиотекой нарушило бы эти условия.

## Этапы проверки CUDA в C

| Функция | Проверка |
|---|---|
| `stt_check_cuda` | Доступность версии C API и общий порядок проверок |
| `require_cuda_provider` | Загруженный ORT действительно содержит `CUDAExecutionProvider` |
| `open_cuda_driver` | Можно открыть `libcuda.so.1`, вызвать `cuInit` и найти устройство |
| `check_cuda_options` | ORT принимает настройки и подключение CUDA provider |
| `copy_ort_error` | Перенос сообщения ORT и освобождение `OrtStatus` |

`dlopen` загружает библиотеку по имени, `dlsym` получает адреса функций драйвера.
Это позволяет сформировать свою диагностическую ошибку вместо предположения,
что наличие строки `provider=cuda` уже означает работающую GPU.

У `check_cuda_options` есть общий блок `cleanup` с освобождением созданных объектов.
Переход `goto cleanup` — обычный приём для C, где нет `defer`.
Он не используется как способ организовать прикладной алгоритм Go.

Проверочная `OrtSessionOptions` не передаётся затем внутрь sherpa.
Она проверяет возможность подключения провайдера. Настройки настоящих
распознавателей создаёт sherpa, а `NVIDIA_TF32_OVERRIDE=0` задаётся для процесса.

Заголовок `onnxruntime_c_api.h` взят из версии 1.20.1 и запрашивает API 20.
Это версия интерфейса, а не требование, что загруженная библиотека обязана
иметь номер 1.20.1: более новая библиотека предоставляет прежние версии API.

Успешная проверка CUDA не доказывает, что каждая операция графа выполняется
на GPU: вспомогательные операции могут оставаться на CPU.

## FP32 и пределы обещаний о качестве

В `main`-версии CPU и CUDA используют FP32-экспорт, без INT8-квантования.
Режим CUDA дополнительно отключает TF32. Это сохраняет выбранную точность
вычислений, но не доказывает побитовое равенство результатов CPU и GPU:
ядра и порядок арифметических операций могут различаться.

Качество речи зависит также от VAD, контекста окна, модели и алгоритма выбора
токенов. Настройка точности — одна часть системы, а не универсальная гарантия
самого низкого WER на любых данных.
