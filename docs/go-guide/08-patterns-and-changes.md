# 8. Паттерны, альтернативы и дальнейшие изменения

[К содержанию](README.md) · [Предыдущая глава](07-build-and-tests.md)

## Какие приёмы действительно применены

Паттерн — повторяемый способ организации решения. Полезнее видеть конкретную
задачу и механизм, чем присваивать каждому типу громкое название.

| Приём | Где применяется | Какую задачу решает |
|---|---|---|
| Передача зависимостей | `newService`, интерфейсы в `stt` | Отделить порядок обработки от FFmpeg и sherpa |
| Адаптер | `transport.GRPC`, `transport.WebSocket`, обёртка sherpa | Согласовать сетевой или библиотечный API с сервисом |
| Пул ресурсов | `gigaam.Model.available` | Повторно использовать дорогие загруженные распознаватели |
| Семафор | `Service.Slots` | Ограничить число одновременно активных обработок |
| Последовательные этапы обработки | Decode → VAD → Buffer → Model | Разделить преобразования данных по ответственности |
| Автомат состояния | `streamFilter`, флаг `Buffer.committed` | Обрабатывать переходы начала/конца речи и смену окон |
| Функция создания объектов | `NewSession`, `NewStream`, `gigaam.New` | Собирать корректное начальное состояние |
| Отложенное создание | `Session.ensureFilter` | Не создавать VAD до первого нуждающегося в нём запроса |
| Явное владение ресурсом | `defer Close/Delete`, `release` | Освобождать ресурсы на разных путях возврата |
| Перевод ошибок на границе | `grpcError`, `recognitionFault` | Стабильные сетевые коды вместо внутренних подробностей |
| Немедленный отказ при ошибке запуска | `run`, `NewSilero`, `checkCUDA` | Не объявлять работоспособным сервис с неверными зависимостями |

Ниже — ограничения этих названий и причины решений.

## Передача зависимостей: ручная и небольшая

Сервису передают `Decoder`, `VAD`, `Model`. Он не создаёт конкретные реализации
и не ищет их через глобальный реестр.

Практический результат виден в тестах: одинаковая `Session` работает с настоящей
моделью и с `recordingModel`, которая только запоминает PCM.
Для подмены не требуется изменять код сессии.

Это также делает точку создания ресурсов очевидной: `main` отвечает за общий
пул, а сессия — за созданный для неё фильтр.

Альтернатива — библиотека автоматического внедрения зависимостей.
Она полезна при большом графе объектов. В этом проекте прямое создание
нескольких объектов читается проще, а ошибки связей на уровне сигнатур
и полей обнаруживает компилятор.

## Адаптер и единая сервисная логика

`GRPC.Transcribe` отвечает за `Recv`, `Send` и status. `Session.Transcribe`
отвечает за звук и текст. Протокол вызывает сервис, а не наоборот.

Если нужно добавить третий транспорт, например HTTP-загрузку файла,
можно создать новую сессию и вызвать независимое распознавание.
Не нужно переносить в HTTP-обработчик алгоритм overlap или создание sherpa stream.

Однако новый транспорт обязан соблюдать условия: порядок сообщений одной сессии,
срок запроса, закрытие VAD и корректную передачу финального результата.
Интерфейс не отменяет эти требования.

## Пул ресурсов не равен пулу горутин

В `available` находятся уже созданные `OfflineRecognizer`.
Отдельные постоянно работающие Go-горутины «worker №1, №2» для них не запускаются.
Модель выполняется в той горутине, которая получила распознаватель.

Отсюда следуют два разных ограничения:

```text
Service.Slots: сколько запросов одновременно выполняют весь путь обработки
Model.available: сколько запросов одновременно используют GigaAM
```

Семафор не ограничивает число запросов в секунду. Если обработка быстрая,
через одно и то же место за секунду пройдёт много запросов.
Для ограничения частоты нужен другой механизм, например счётчик или выдача
разрешений с заданной скоростью. В этой версии его нет.

## Последовательные этапы не означают отдельную горутину на этап

Слово «конвейер» здесь описывает порядок преобразований.
В одном запросе `Decode`, `Accept` и `Transcribe` вызываются обычными функциями.
Между ними нет цепочки фоновых каналов с задачами.

Каналы между всеми этапами добавили бы очереди, управление завершением
и владением массивами. Для обработки независимых окон в большом потоке задач
такая схема могла бы быть полезна. Здесь последовательный вызов упрощает
контекст запроса, порядок аудио и освобождение ресурсов.

## Автомат состояния без иерархии классов

`streamFilter` выбирает действия по `active`, выходу детектора и содержимому
`pending/prefix`. `Buffer` — по `committed`, счётчику и длине.
Это автоматы состояния, выраженные полями и ветвлениями.

Здесь нет отдельных типов `WaitingState`, `SpeakingState` с виртуальными методами.
Поэтому называть код полной реализацией классического объектного State pattern
нет необходимости. Для двух простых состояний ветвления легче проследить.

Если появятся сложные переходы — несколько независимых стадий подтверждения,
восстановление, перенос состояния, — явный перечислимый тип состояния и таблица
переходов могут стать понятнее набора взаимосвязанных флагов.

## Функции `New...` и владение

Функция создания объекта скрывает детали начального состояния:
канал нужной вместимости, буфер с пересчитанными миллисекундами,
настройки нативного VAD. Это практическая функция создания, а не обязательно
сложная иерархия «фабрик».

У `NewSession` нет ошибки, потому что она создаёт только Go-объекты.
У `NewStream` есть ошибка, потому что загрузка нативного детектора может не удаться.

В проекте действует полезное правило владения:

| Кто создаёт | Что создаёт | Кто закрывает |
|---|---|---|
| `main.run` | Пул GigaAM, listener | `defer` внутри `run` |
| Транспорт | Сессию клиента | `defer session.Close()` |
| Сессия | Постоянный VAD потока | `Session.Close` |
| Независимое распознавание | Временный VAD | `defer filter.Close()` |
| `Model.Transcribe` | Временный sherpa stream | `defer DeleteOfflineStream` |
| WebSocket-обёртка | Ping ticker и подключение | `defer Stop`, `release`, `Close` |

Здесь нет надежды, что сборщик мусора Go своевременно вызовет нативное удаление.
Также не следует называть `defer` полным аналогом C++-деструктора:
он привязан к выходу функции, а не к концу произвольной области видимости.

## Почему отдельная сессия лучше глобального буфера

Глобальный буфер смешивал бы звук клиентов. Общий mutex упорядочил бы доступ,
но по-прежнему оставил бы один общий речевой контекст.

Сессия связывает состояние с владельцем: один gRPC-stream или одно WebSocket-соединение.
Благодаря этому разрыв соединения имеет понятное действие — закрыть его сессию.

Сохранение состояния в Redis или базе данных позволило бы переживать перезапуск,
но одной сериализации PCM недостаточно для сохранения нативного состояния Silero.
Потребовались бы правила восстановления, идентификаторы сессий и согласование
порядка запросов. В текущем контракте таких требований нет.

## Почему интерфейсы маленькие

`Model` в пакете `stt` содержит только `Transcribe`. Метод `Close` ему не нужен:
общей моделью владеет `main`, а не отдельная сессия.

Если добавить `Close` в этот интерфейс только потому, что он существует
у конкретной GigaAM, сессия получит лишнюю возможность закрыть общий ресурс.
Маленький интерфейс показывает границы ответственности и облегчает тестовую замену.

Для VAD другая ситуация: сессия создаёт фильтр, поэтому `audio.Filter`
включает `Close`. Интерфейсы похожи не по внешнему стилю, а по необходимым действиям.

## Какие альтернативы разумны и что они меняют

| Текущее решение | Альтернатива | Польза альтернативы | Цена или ограничение |
|---|---|---|---|
| FFmpeg-процесс на сегмент | Прямой вызов библиотек кодеков | Меньше запусков процесса | Сложнее декодирование и управление C-памятью |
| GigaAM внутри процесса | Отдельный сервер моделей | Общая инфраструктура моделей, возможный batching | Сетевой обмен и отдельная эксплуатация |
| Пул распознавателей | Один распознаватель под mutex | Проще и меньше памяти | Один одновременный инференс |
| Синхронный запрос с контекстом | Очередь длительных заданий | Можно переживать разрыв клиента | Другой API и хранение заданий |
| Повторное распознавание окна | Истинная потоковая модель | Меньше повторных вычислений | Другая модель, состояние и проверка качества |
| Конфигурация через окружение | Файл YAML/TOML | Удобны сложные вложенные настройки | Ещё один формат, источник и правила приоритета |
| Ручная проверка JSON-RPC | Универсальная RPC-библиотека | Меньше собственного разбора | Нужно проверить точную совместимость существующего API |
| `[]byte` PCM и явное преобразование | Общие буферы и небезопасные представления | Возможна экономия выделений | Сложнее владение, риск гонок, форматы всё равно различаются |

Таблица объясняет компромиссы. Она не утверждает, что текущий вариант
во всех случаях быстрее каждой альтернативы.

## Где изменять конкретное поведение

### Добавить параметр конфигурации

1. Добавить поле в `Config`.
2. Прочитать значение в подходящем методе `FromEnv`.
3. Проверить диапазон и связи с другими параметрами.
4. Передать его при создании нужного объекта в `main`.
5. Обновить `.env.example`, документацию и проверки ошибочных значений.

Избегайте чтения окружения в каждой обработке: иначе поведение становится
скрытым и сложнее воспроизводится в тестах.

### Изменить момент финального ответа

Смотреть `Session.recognizeWindow`, `Flush` и правила `Buffer.Commit/Clear`.
Изменение только gRPC или JSON-RPC-адаптера создаст разное предметное поведение
у двух протоколов.

Проверить нужно минимум четыре случая: заполнение окна, подтверждённая пауза,
окончание отправки с неполным VAD-окном, окончание после уже выданного `message`.

### Добавить протокол

Нужен новый адаптер к `stt.Service`, отдельный жизненный цикл сервера и решение,
как клиент обозначает завершение отправки. Необходимо сохранить `Close`
на ошибках и не вызывать одну `Session` параллельно без организации порядка.

### Заменить VAD

Новая реализация должна создавать независимый `audio.Filter` для потока.
Проверяются сохранение границ, `Flush`, отсутствие искусственных нулей
в выходном PCM и освобождение нативных ресурсов.
Само совпадение сигнатур методов ещё не означает совпадение этой семантики.

### Заменить модель

Новая реализация `stt.Model` может сохранить сервисный контракт PCM → текст.
Но нужно согласовать допустимую длительность, частоту, поведение пустого PCM,
отмену и время жизни ресурсов. Если новая модель действительно потоковая,
одного текущего интерфейса для сохранения её состояния может не хватить.

## Как не сломать владение памятью при оптимизации

`Buffer.Sample()` возвращает существующий срез. Текущая модель читает его
синхронно и преобразует в новый массив `float32`.

Если заменить модель асинхронной отправкой и сразу продолжить менять буфер,
прежнее предположение станет неверным: потребуются копия входа либо явная
передача владения массивом до окончания фоновой работы.

Аналогично нельзя возвращать распознаватель в пул по тайм-ауту клиента,
если C++ ещё выполняет `Decode` на нём. Ограничение срока ожидания и прекращение
фактических вычислений — разные задачи.

## Как читать проверки и диагностику

Если проблема похожа на повреждённое аудио, начинать стоит с `Processor.Decode`
и `ErrAudio`. Если потерян конец фразы — с VAD pending/sent и `Session.Flush`.
Если клиент ждёт под нагрузкой — с `Slots`, пула и сроков контекста.
Если возникает ошибка размеров ONNX — с экспорта и форм входа конкретного графа.

Не следует связывать любую ошибку модели с уровнем логирования или числом горутин.
Числовая форма тензора, кодек, сетевой контракт и управление ресурсами — разные
части системы. Хорошая диагностика сначала определяет часть, где нарушен контракт.

## Что важно удерживать при дальнейшем развитии

Программа организована вокруг нескольких конкретных правил:

1. После декодирования звук имеет один формат.
2. Состояние речи принадлежит конкретному клиентскому потоку.
3. GigaAM загружена заранее и выдаётся запросам из пула.
4. Конкурентная работа ограничена, ожидание учитывает срок запроса.
5. Финализация сохраняет реальные отложенные отсчёты.
6. Сетевые различия не должны дублировать алгоритм обработки речи.
7. Нативные ресурсы закрываются явно.
8. Тесты порядка обработки отделены от проверок настоящих моделей.

Именно эти правила, а не названия паттернов сами по себе, объясняют большую
часть конструкции проекта.
