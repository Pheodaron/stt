## Точка входа: почему есть `main` и `run`

В `main` создаётся контекст, связанный с сигналами процесса:

```go
ctx, cancel := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer cancel()

if err := run(ctx); err != nil {
    slog.Error("server stopped", "error", err)
    os.Exit(1)
}
```

`context.Background()` — исходный контекст без срока и отмены.
`signal.NotifyContext` создаёт дочерний контекст: при Ctrl+C или SIGTERM
его канал `Done()` закрывается. Серверные функции ждут этот сигнал.

`main` не может вернуть `error`, поэтому основная работа вынесена в `run`.
Она возвращает ошибку обычным способом; `main` решает, с каким кодом завершить процесс.
Это отделяет запуск приложения от последнего действия `os.Exit`.

Вызовы `defer` внутри `run` выполнятся до её возврата в `main`.
После `os.Exit(1)` отложенные вызовы самой `main` уже не выполняются.

Альтернатива — сразу вызывать `log.Fatal` глубоко внутри функций.
Тогда нижний слой сам завершает процесс и не даёт вызывающему коду закрыть ресурсы.
Возврат ошибки оставляет управление жизненным циклом в одном месте.

## Порядок инициализации

`run` выполняет действия последовательно:

1. Читает и проверяет конфигурацию.
2. Настраивает `slog`.
3. Проверяет наличие исполняемого файла FFmpeg через `exec.LookPath`.
4. Загружает пул GigaAM через `gigaam.New`.
5. Проверяет Silero через `audio.NewSilero`.
6. Открывает TCP-порт через `net.Listen`.
7. Создаёт общий `stt.Service`.
8. Пишет сообщение `ready`.
9. Запускает выбранный сервер: gRPC либо HTTP/WebSocket.

Уже полученные ресурсы закрываются через `defer`:

```go
model, err := gigaam.New(cfg)
if err != nil {
    return err
}
defer model.Close()
```

Если после загрузки модели не удастся открыть порт, модель всё равно будет закрыта.
Такая последовательность позволяет обнаружить ошибки модели до объявления готовности.

`ready` означает, что прошли предусмотренные проверки и открыт listener.
Это не результат контрольного распознавания настоящей записи. Вызов `Serve`
следует сразу после этого сообщения; небольшой промежуток между ними существует.

## В одном процессе выбирается один сетевой режим

```go
if cfg.ClientType == "websocket" {
    return serveWebSocket(ctx, listener, service, cfg)
}
return serveGRPC(ctx, listener, service, cfg)
```

Сервис не запускает gRPC и WebSocket одновременно на одном порту.
`CLIENT_TYPE` проверяется заранее и допускает только `grpc` или `websocket`.

Общая обработка звука от этого выбора не меняется: обе ветви получают один
и тот же `service`. Меняется способ получения запроса и отправки ответа.

Альтернатива — два listener или совмещение протоколов в одном HTTP-сервере.
Это расширило бы возможности, но добавило бы настройки адресов, маршрутизацию
и более сложную остановку. В этой версии такой задачи нет.

## `newService`: где соединяются реализации

Фрагмент создаваемого значения:

```go
return &stt.Service{
    Decoder:    processor,
    VAD:        vad,
    Model:      model,
    BufferSize: cfg.BufferSize,
    OverlapMS:  cfg.OverlapMS,
    MaxSeconds: cfg.MaxAudioSeconds,
    Timeout:    cfg.RequestTimeout,
    Slots:      make(chan struct{}, cfg.ModelWorkers*2),
}
```

В полях интерфейсных типов оказываются конкретные объекты. Это ручная передача
зависимостей: внешняя функция создаёт их и передаёт тому, кто ими пользуется.
Сессия не ищет модель в глобальной переменной и не создаёт FFmpeg самостоятельно.

Для трёх зависимостей отдельная библиотека контейнера зависимостей дала бы мало
пользы. Обычный литерал показывает все связи в одном месте и проверяется компилятором.

## Откуда берутся настройки

`config.FromEnv()` читает окружение процесса. Сам Go-сервер не разбирает `.env`.
Файл `.env` передаёт Compose через `env_file`; для обычного процесса значения
должны быть установлены другим способом.

Функция чтения:

```go
func value(key, fallback string) string {
    if s, ok := os.LookupEnv(key); ok {
        return s
    }
    return fallback
}
```

`LookupEnv` возвращает значение и признак наличия. Поэтому отсутствующая переменная
и заданная пустая переменная ведут себя по-разному:

| Окружение | `value("PORT", "8080")` | Результат проверки |
|---|---|---|
| `PORT` отсутствует | `"8080"` | Корректный порт |
| `PORT=9000` | `"9000"` | Корректный порт |
| `PORT=` | `""` | Ошибка преобразования/проверки порта |

Это помогает не маскировать ошибочно заполненную конфигурацию значением по умолчанию.
С другой стороны, если требуется трактовать пустую строку как отсутствие настройки,
текущая функция этого не делает.

## Три вида настроек

| Вид | Примеры | Как читается |
|---|---|---|
| Строка | `CLIENT_TYPE`, `MODEL_PROVIDER`, путь FFmpeg | `value` |
| Целое число | `MODEL_WORKERS`, `BUFFER_SIZE` | `strconv.Atoi` |
| Время | `REQUEST_TIMEOUT`, `PING_INTERVAL` | Целое число секунд → `time.Duration` |

`time.Duration` хранит длительность в наносекундах. Поэтому запись
`time.Duration(seconds) * time.Second` важна: просто `time.Duration(60)`
означала бы 60 наносекунд, а не минуту.

Для `VAD_THRESHOLD` используется `strconv.ParseFloat(..., 32)`.
Отдельно отклоняются `NaN`, бесконечности и значения вне диапазона.
Одного сравнения `threshold < 0.01` недостаточно для `NaN`: сравнения с ним
не работают как с обычным числом.

## Почему целые параметры читаются таблицей

Сокращённая форма таблицы `readIntegers`:

```go
settings := []struct {
    key      string
    target   *int
    fallback int
}{
    {"BUFFER_SIZE", &c.BufferSize, 10},
    {"NUM_THREADS", &c.NumThreads, 2},
    {"MODEL_WORKERS", &c.ModelWorkers, 1},
}
```

Каждая строка хранит имя переменной, адрес поля и значение по умолчанию.
Цикл преобразует строку в число и записывает его через `*setting.target`.
Получатель `func (c *Config)` позволяет менять исходную конфигурацию.

Альтернатива — девять почти одинаковых блоков `Atoi` и проверки `err`.
Таблица уменьшает повторение. Она не подменяет предметные проверки: допустимые
диапазоны остаются в `validateInference`, `validateServer`, `validateAudio`.

## Значение в коде и значение в `.env.example`

Их нельзя смешивать. Например:

| Параметр | Если окружение не задано | В `.env.example` |
|---|---:|---:|
| `BUFFER_SIZE` | 10 | 4 |
| `MODEL_WORKERS` | 1 | 1 |
| `NUM_THREADS` | 2 | 2 |
| `MAX_AUDIO_SECONDS` | 25 | 25 |
| `PADDING_DURATION_MS` | 250 | 250 |
| `BUFFER_OVERLAP_MS` | 500 | 500 |
| `REQUEST_TIMEOUT` | 60 секунд | 60 секунд |

В примерах дальнейших глав `BUFFER_SIZE=4` указан явно, если используется
пример конфигурации контейнера.

`HOST_PORT` и `GPU_DEVICE_ID` относятся к Compose на хосте. `PORT` и `URL`
относятся к слушающему сокету внутри контейнера. Менять `HOST_PORT` на 8081
не означает менять внутренний порт сервера.

## Проверки согласованности

`Validate` запускает три группы проверок. Среди важных связей:

- `MODEL_PROVIDER` — `cpu` либо `cuda`, без неявного режима `auto`.
- `MODEL_PRECISION` — `fp32` либо `int8`; CUDA-профиль допускает только `fp32`.
- `NUM_THREADS` — от 1 до 64, `MODEL_WORKERS` — от 1 до 16.
- `MAX_AUDIO_SECONDS` — от 1 до 25.
- Padding — от 64 до 2000 мс; пауза окончания речи должна быть не короче padding
  и не длиннее 3000 мс.
- Перекрытие окон — от 0 до 2000 мс и строго меньше максимальной длины окна.

Для сборки путей используется `filepath.Join`. Для адреса — `net.JoinHostPort`.
Второй корректно обрабатывает IPv6, где простое `host + ":" + port` неоднозначно.

`MODEL_PRECISION=fp32` выбирает пути обычного ONNX-экспорта. Это не универсальная
команда ONNX Runtime «приведи любые переданные веса к FP32». Если подменить файлы,
реальный граф определяется содержимым файлов, а не названием настройки.

## Логирование

Используется стандартный `log/slog`: текстовый обработчик и пары ключ–значение.
Поля `provider`, `threads`, `workers` помогают понять, с какими настройками
фактически запущен процесс.

`LOG_LEVEL=critical` преобразуется в `slog.LevelError`: отдельного уровня critical
в этой конфигурации нет. Уровень журнала не меняет размеры тензоров или алгоритм модели.

По сравнению с неструктурированным `fmt.Println` пары ключ–значение проще
фильтровать. Внешняя библиотека журналирования здесь не обязательна:
используемые возможности уже есть в стандартной библиотеке.

## Остановка gRPC

`server.Serve(listener)` блокирует вызывающую горутину, поэтому его запускают отдельно:

```go
done := make(chan error, 1)
go func() {
    done <- server.Serve(listener)
}()
```

Основная горутина делает `select`: ждёт ошибку сервера либо отмену общего контекста.
Канал имеет вместимость 1, чтобы серверная горутина смогла отправить результат,
даже если другая ветвь `select` уже начала остановку.

При сигнале health check переводится из готового состояния, затем вызывается
`GracefulStop`: существующим RPC дают завершиться. Если за 10 секунд это не произошло,
вызывается принудительный `Stop`.

Длительный gRPC-поток может удерживать мягкую остановку до этого предела.
Уже начатый вызов C++ не прерывается только оттого, что транспорт отменил контекст;
ограничения нативного вызова разобраны в главе 5.

## Остановка HTTP и WebSocket

У HTTP-сервера есть `ReadHeaderTimeout=10s`: ограничено ожидание заголовков
при новом HTTP-соединении. Это не общий срок распознавания аудио.

Перед `http.Server.Shutdown` явно вызывается `websocket.Close()`.
После перехода HTTP-соединения в WebSocket обычная остановка HTTP-сервера
не управляет им как обычным незавершённым HTTP-запросом. Поэтому WebSocket-обёртка
хранит собственный список соединений и закрывает их отдельно.

`stopHTTP` создаёт новый контекст от `context.Background()`, а не от уже
отменённого контекста сервера. Иначе мягкая остановка получила бы отмену сразу.
Если за 10 секунд `Shutdown` не завершился, вызывается `server.Close()`.

В режиме WebSocket `/healthz` возвращает `{"status":"ok"}`.
В режиме gRPC используются стандартный health service и reflection.
Это два разных способа проверки готовности для двух разных сетевых режимов.
