# Выбор CPU-инференса GigaAM

Проверено 15 октября 2026. Цель — сохранить `v3_e2e_rnnt` исходного сервиса,
обойтись без Python при запуске и подобрать практичный вариант для CPU.

## Решение

Основной вариант изменён по приоритету пользователя: **полная GigaAM v3 E2E RNNT,
все веса FP32, без квантования**, sherpa-onnx 1.13.8, CPU execution provider.
Декодер `greedy_search` соответствует исходному GigaAM RNNT-пути;
утверждения, что он даёт максимальную точность среди всех вариантов декодирования,
нет. Дефолт — один recognizer и предварительно два потока; оптимум для FP32
нужно измерить после получения весов.

`mise run model` готовит FP32 из исходного checkpoint. Закреплённый upstream exporter
адаптируется без вызова quantize_dynamic, модель загружается на CPU без FP16,
декодер экспортируется для batch=1. Скрипт проверяет отсутствие квантованных
операторов и FP16/BF16 инициализаторов. Python нужен только для этого экспорта;
Go-сервер использует готовые ONNX-файлы без Python.

**Блокировка проверки:** хост исходных весов `cdn.chatwm.opensmodel.sberdevices.ru`
не разрешён сетевой политикой текущего окружения (CONNECT HTTP 403).
FP32-веса не получены, реальный инференс и замеры FP32 пока не выполнены.

Это обоснованный выбор для данного переноса, а не доказательство абсолютного
первенства среди всех движков. Сравнительного замера с PyTorch, OpenVINO и прямым
ORT на тех же неквантованных весах и корпусе здесь нет. Оптимальное число потоков
и выигрыш INT8 зависят от CPU, формы графа, длины аудио и нагрузки.

| Вариант | Вывод для этого проекта |
|---|---|
| PyTorch из исходника | Работает с `.ckpt`, но сохраняет Python/PyTorch runtime; не соответствует задаче переноса сервиса без Python |
| Прямой ONNX Runtime из Go | Возможен; нужны точная обработка признаков, цикл RNNT и декодирование токенов. Это тот же вычислительный runtime, на котором работает выбранная sherpa-сборка; отдельного доказательства, что такой путь медленнее, нет |
| sherpa-onnx + GigaAM FP32 | Основной вариант: исходные веса без потерь от квантования; конфигурация и подготовка экспортера готовы, запуск ожидает доступ к весам |
| sherpa-onnx + GigaAM INT8 | Предыдущий вариант, проверен реальным распознаванием; остаётся отдельной опцией, не выбран по умолчанию |
| OpenVINO / другие providers | Могут быть конкурентоспособны на подходящем CPU; в этой работе не проверены |

Решение не подменяет RNNT на CTC. GigaAM CTC тоже поддерживается sherpa и потенциально
может дать другую скорость, но это смена акустической модели и компромисс по качеству.
Для исходного RNNT нужна отдельная проверка WER/CER на записях пользователя;
INT8 не гарантирует идентичный текст по сравнению с исходным PyTorch FP32/FP16.

## Источники и совместимость

- [Официальный Go API sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/go-api/index.html):
  готовые нативные библиотеки, CGO, offline и streaming API.
- [Официальный экспорт GigaAM v3 E2E RNNT](https://github.com/k2-fsa/sherpa-onnx/blob/fa29eb91c80335fc70af869a7bb459578f90e5ad/scripts/nemo/GigaAM/export-onnx-rnnt-v3-punct.py):
  64 log-mel признака, metadata `is_giga_am`, квантование энкодера QUInt8,
  специальный интерфейс декодера и `tokens.txt` с blank-токеном.
- [Декодер NeMo transducer в sherpa](https://github.com/k2-fsa/sherpa-onnx/blob/fa29eb91c80335fc70af869a7bb459578f90e5ad/sherpa-onnx/csrc/offline-transducer-greedy-search-nemo-decoder.cc):
  greedy RNNT реализован в C++, без Python-цикла и внешних вызовов на каждый токен.
- [Исходный ONNX-путь GigaAM](https://github.com/salute-developers/GigaAM/blob/7447938d791c4f3e643386ee22c33777004293a5/gigaam/onnx_utils.py):
  позволяет проверить семантику модели, но его экспорт отличается от sherpa-экспорта.
- [Обсуждение производительности GigaAM в sherpa](https://github.com/k2-fsa/sherpa-onnx/issues/2151):
  отдельные сообщения пользователей не дают воспроизводимого сравнительного
  бенчмарка; цифры оттуда не используются как доказательство выбора.

Модель: `sherpa-onnx-nemo-transducer-punct-giga-am-v3-russian-2025-12-16`
из [официального релиза asr-models](https://github.com/k2-fsa/sherpa-onnx/releases/tag/asr-models).
SHA-256 архива: `f9620a0099019c6afcee26525ef9ed3297fa50dd5691c1902af0c948fc1a470b`.
Размер runtime-ассетов около 222 MiB; это размер файлов, не пиковый RSS процесса.

## Предыдущий локальный замер — только INT8

Ниже приведена история замеров квантованной модели. Эти цифры не относятся
к новому FP32-режиму и не используются как оценка его скорости.

Среда: Linux amd64, AMD EPYC 9V74, видны 3 vCPU, cgroup `cpu.max=200000 100000`
(квота 2 CPU), AVX2/AVX-512. Go 1.25.1, sherpa-onnx Go 1.13.8.
Аудио: `test_wavs/example.wav` из архива модели, 11,29 с. Оно декодировано
FFmpeg в mono PCM16 16 кГц один раз. Для каждого числа потоков создаётся новый
recognizer, выполняется один прогрев, затем пять последовательных итераций.
Другие проверки/сборки на время замера не запускались намеренно, но среда общая
и шум планировщика не исключён. Исходные результаты: [cpu-benchmark.jsonl](cpu-benchmark.jsonl).

| NUM_THREADS | Медиана, с | RTF | Скорость относительно реального времени |
|---:|---:|---:|---:|
| 1 | 1,185 | 0,105 | 9,5× |
| 2 | 0,780 | 0,069 | 14,5× |
| 4 | 1,715 | 0,152 | 6,6× |

Два потока здесь примерно в 1,52 раза быстрее одного. Четыре выходят за CPU-квоту
и дают худший результат. На всех измеренных итерациях получен один и тот же текст
с пунктуацией; это smoke-проверка, а не оценка точности на корпусе.
RTF не включает загрузку модели (~0,68..0,79 с), FFmpeg, VAD, сеть и повторные
распознавания перекрывающихся окон, поэтому не является оценкой полной нагрузки сервиса.

Пример воспроизведения после скачивания модели (для замера используйте вашу запись
или WAV из исходного архива модели):

```bash
go run ./cmd/stt-bench -file /path/to/speech.wav -threads 1,2,4 -runs 5
```

Для окончательной настройки FP32-сервера сначала повторите замер на его весах,
затем измерьте p50/p95 задержки и RSS при
реальном числе клиентов, коротких чанках и выбранном `BUFFER_SIZE`. Увеличение
`MODEL_WORKERS` создаёт дополнительные экземпляры модели и увеличивает память;
при квоте 2 CPU стартовать следует с `MODEL_WORKERS=1`, `NUM_THREADS=2`.
