# План: расшифровка полной встречи

Статус: проектные решения реализованы для CPU в ветке `diarization`; эксплуатационный контракт и ограничения проверок — в [meeting-transcription.md](meeting-transcription.md). GPU Nemotron остаётся следующим этапом.

## 1. Зафиксированные решения

- Только gRPC, client-streaming: аудиофайл передаётся последовательностью сообщений, один полный результат возвращается после обработки.
- Обработка синхронная в обработчике RPC. Фоновых заданий, очереди встреч и worker-горутины нет.
- Nemotron-3-Diarization через официальный C ABI NeMo-Speech.cpp и cgo.
- GigaAM v3 E2E RNNT FP32 через существующий sherpa-onnx. Один общий экземпляр GigaAM для встреч и живого режима.
- Сначала рабочий CPU-контейнер. GPU — следующий этап.
- Nemotron в официальном GGUF-профиле `--outtype f32`, GigaAM и Silero запекаются в контейнер. Для Nemotron этот профиль допускает один штатный F16-вес свёртки `subpixel_upsample.weight`, необходимый CPU backend; фактические типы фиксируются в manifest. Сеть при запуске не нужна.
- Одна принятая встреча на экземпляр сервиса, от входа в handler до завершения `SendAndClose`. Следующая получает `ResourceExhausted` до первого `Recv`.
- Живые запросы имеют приоритет между вызовами GigaAM. Выполняющийся native Decode не прерывается.
- В смешанном фрагменте возвращаются все обнаруженные спикеры. Текст распознаётся один раз, без распределения слов между ними.
- Прикладного ограничения размера файла и ограничения длительности в два часа не вводим. Два часа — обязательный проверочный сценарий.

**Размер загрузки:** суммарный размер файла не ограничивается размером одного protobuf-сообщения. Стартовый размер чанка — 1 MiB; он ограничивает данные одного сообщения, а не всей встречи. Сервер последовательно пишет чанки на диск. После окончания загрузки в том же RPC выполняются декодирование, диаризация и ASR. Полный ответ остаётся одним сообщением: его размер должен быть меньше 2 GiB. Объём диска, RAM для результата и deadline также конечны.

## 2. Результат критического разбора

| Проблема | Решение |
|---|---|
| Повышение старых лимитов сломает смысл живых чанков | Отдельные параметры встречи; старые 25 секунд и лимиты чанков сохраняются |
| Целый файл не помещается в одно protobuf-сообщение | Передавать файл через client-streaming по 1 MiB; счётчик общей длины — `uint64` |
| Несколько клиентов могут одновременно загружать файлы | Захватывать единственный слот встречи в stream handler до первого `Recv`, занятым отвечать сразу |
| Накопление чанков возвращает зависимость RAM от размера файла | Записывать каждый чанк до следующего `Recv`, не собирать общий bytes-буфер; PCM хранить на диске, float32 создавать блоками |
| FFmpeg собран только с протоколом pipe | Включить file; открывать сохранённый файл как seekable-вход, выводить PCM через stdout |
| VAD удаляет паузы и теряет время | Полную запись не пропускать через текущие `Session` и фильтр склейки PCM |
| Диаризация не разделяет голоса | Пересечения возвращать с массивом спикеров и неоднозначным авторством текста |
| GigaAM возвращает строку без времени слов | Время относится к фрагменту; word timestamps в первую версию не входят |
| Nemotron сворачивает старые вероятности примерно после 20 минут | Для всей встречи использовать одинаковую штатную сегментацию SDK; не применять новые пороги только к финальному хвосту |
| Отмена context не останавливает текущий cgo-вызов | Проверять отмену между вызовами; не освобождать модель и слот вычисления до фактического возврата native |
| Приоритет GigaAM не устраняет конкуренцию за CPU | Ограничивать параллельность, измерять задержки живого режима под нагрузкой; строгий SLA не обещать |
| Максимум восемь голосов | Зафиксировать ограничение модели; обнаружение девятого голоса не гарантируется |

## 3. Контракт gRPC

В существующий `service Gigaam` добавить:

```proto
rpc TranscribeMeeting(stream MeetingRequest) returns (MeetingResponse);

message MeetingUploadHeader {
  uint64 size_bytes = 1;
}

message MeetingRequest {
  oneof payload {
    MeetingUploadHeader header = 1;
    bytes chunk = 2;
  }
}
```

Последовательность загрузки:

1. Первое сообщение — `header` с фактическим размером файла в байтах, больше нуля.
2. Следующие сообщения — непустые `chunk` в исходном порядке; по умолчанию до 1 MiB данных, последний может быть короче.
3. Клиент закрывает отправку и ждёт результат. Для Go — последовательные `Send`, затем `CloseAndRecv`.
4. Сервер при `io.EOF` сверяет фактически принятые байты с `size_bytes`, закрывает файл и начинает обработку.
5. После обработки сервер вызывает один `SendAndClose` с полным `MeetingResponse`.

Повторный header, chunk до header, пустой чанк, превышение размера чанка и несовпадение общей длины — ошибки запроса. Общий размер не резервируется в RAM. Счётчик проверяется на переполнение. Порядок обеспечивает gRPC, поэтому номера чанков и offset в первой версии не нужны. Возобновление оборванной загрузки не входит в первую версию.

**Размер чанка:** 1 MiB — стартовый компромисс между числом RPC-сообщений и расходом памяти, а не измеренный оптимум. Перед завершением реализации сравнить 256 KiB, 1 MiB и 4 MiB на целевой сети: throughput, CPU и peak RSS. Размер задаётся общей настройкой `MEETING_CHUNK_BYTES` сервера и клиента; клиент может присылать меньшие чанки.

Клиент читает файл по одному чанку и последовательно отправляет сообщения, не накапливая весь файл. Данные уже переданного в `Send` сообщения не изменять; при повторном использовании буфера чтения копировать чанк в отдельный буфер сообщения. Сервер пишет чанк на диск до следующего `Recv`. Последовательность `Send`/`Recv` и HTTP/2 flow control ограничивают накопление данных. Чанки — произвольные диапазоны байтов контейнера, а не самостоятельные WAV или ASR-фрагменты. FFmpeg получает собранный исходный файл после завершения загрузки.

`MeetingResponse`:

- `duration_ms` — длительность декодированной записи;
- `speaker_ids` — все обнаруженные спикеры, идентификаторы 1..8;
- `diarization` — интервалы `{start_ms, end_ms, speaker_id}`, включая пересечения;
- `segments` — расшифровка `{start_ms, end_ms, speaker_ids, text, has_overlap, forced_split}`.

Правила:

- `speaker_ids` каждого текстового фрагмента содержит объединение всех голосов, обнаруженных в его речевом диапазоне.
- При нескольких спикерах текст принадлежит фрагменту целиком; авторство отдельных слов неизвестно.
- `has_overlap` означает обнаруженную одновременную активность, а не успешное распознавание всех голосов.
- Время — относительно начала декодированной аудиозаписи, не календарное время. Имена и участники ВКС автоматически не определяются.
- Ответ содержит весь результат. При ошибке pipeline возвращается gRPC status, без частичной успешной расшифровки.
- Запись без обнаруженной речи возвращает длительность и пустые списки.
- Старые wire-имена и protobuf-поля не меняются. Для WebSocket новый метод не добавляется.

## 4. Приём и декодирование

1. В начале stream handler проверить context и неблокирующе занять единственный слот встречи, до первого `Recv`; освобождение — через `defer` после реального завершения handler.
2. Принять и проверить header, создать приватный временный каталог и файл исходника.
3. В цикле `Recv` проверять context, тип и длину чанка; синхронно записывать его в файл, обновлять счётчик. После `io.EOF` сверить полную длину. Не накапливать чанки в списке или общем буфере.
4. FFmpeg открывает локальный seekable-файл; выбрать первую аудиодорожку, получить mono PCM16LE 16 kHz.
5. Записывать stdout последовательно в PCM-файл через context-aware writer. Не накапливать полный PCM в `bytes.Buffer`.
6. Сохранять паузы и порядок отсчётов. Не обрезать начало, конец или хвост ради лимитов текущего `Processor`.
7. Длительность вычислять по фактическому числу PCM-отсчётов. Смещения и длительности внутри pipeline хранить в `int64`.
8. Закрыть FFmpeg и файлы. Исходник после успешного декодирования удалить; PCM сохранять до окончания ASR.

Файловый decoder — отдельный путь, не повышение `MaxAudioSeconds` текущего декодера. Разрешённые протоколы FFmpeg — только нужные локальные file/pipe. Обработку реальных WAV, MP3, OGG/Opus, FLAC и M4A подтвердить тестами встроенного FFmpeg.

Для двух часов PCM16 требуется около 230,4 MB диска. До удаления исходника диск одновременно содержит исходный файл и PCM. Это не оценка всей RAM сервиса.

## 5. Nemotron и cgo

При запуске gRPC-сервиса:

- загрузить GGUF F32 из `/app/models/nemotron-3-diarization-f32/model.gguf`;
- создать модель через `nemo_speech_diar_create`, CPU: `gpu=-1`, preset: `v3-offline`;
- проверить, что загружена восьмиголосная модель нужного формата;
- объявить readiness после успешной загрузки обеих моделей.

На встречу:

```text
stream_open
  → читать PCM16 блоками, например по 1 секунде
  → преобразовывать текущий блок в float32
  → stream_push_f32, сохраняя одну сессию на весь файл
  → stream_finish
  → diar_segments: запрос количества, затем получение интервалов
  → скопировать интервалы в Go
  → stream_close
```

Внутренние окна и speaker cache управляются SDK. Файл не делится на независимые сессии. `diar_offline_f32` для длинной записи не применяется.

Go-обвязка:

- использует только публичный C ABI и закреплённые заголовки;
- инициализирует `size` конфигураций, проверяет каждый status;
- копирует thread-local текст ошибки в том же C-вызове, где произошла ошибка;
- не оставляет указатели на Go-память в native-коде между вызовами;
- закрывает сессию при любом выходе, модель — после завершения всех вызовов;
- сохраняет штатные настройки сегментации для всей записи, включая свёрнутую историю.

Не обещать отдельный параметр числа CPU-потоков Nemotron, пока его поддержка не проверена в закреплённом standalone C API. Текущий `NUM_THREADS` относится к GigaAM.

## 6. Подготовка фрагментов GigaAM

Хранить разметку диаризации отдельно от списка ASR-фрагментов.

1. Проверить native-интервалы: конечные числа, корректный порядок, границы внутри записи; перевести секунды в отсчёты.
2. По всем границам построить непересекающиеся речевые участки с набором активных спикеров. Сами исходные интервалы спикеров сохранить.
3. Объединять соседние участки с одинаковым набором спикеров. Паузы при объединении остаются в исходном PCM; речь другого человека не вырезается и не склеивается.
4. Короткое пересечение менее 1 секунды можно объединить с соседними участками для контекста, если общий фрагмент укладывается в ASR-лимит. Поглощённые участки отдельно не распознавать. У результата — все спикеры объединённого диапазона и неоднозначное авторство.
5. Длинные фрагменты делить в пределах `MAX_AUDIO_SECONDS`, максимум 25 секунд вместе с padding. Искать точку в паузе перед пределом; для этого использовать отдельный анализ пауз Silero без удаления PCM и с сохранением смещений.
6. Если паузы нет, выполнить принудительный разрез и выставить `forced_split`. Перекрывающиеся ASR-окна и эвристическое удаление повторов в первую версию не включать.
7. Padding до 200 ms добавлять только в подтверждённую соседнюю тишину. Не заходить в речь другого голоса и не выходить за ASR-лимит.
8. Прочитать соответствующий диапазон PCM-файла и один раз вызвать существующий `Model.Transcribe`.
9. Сохранить текст, исходные границы, набор спикеров и признаки; вернуть фрагменты в хронологическом порядке.

Короткие реплики не отбрасывать только из-за длины. Внутри хранить отдельно речевой диапазон и фактический диапазон входа ASR с padding.

Для пересечения двух голосов GigaAM слышит смесь. Два одинаковых вызова не выделяют двух говорящих. В первой версии нет source separation и гарантии распознавания обеих реплик.

## 7. Планирование вычислений

- Один общий пул GigaAM, по умолчанию `MODEL_WORKERS=1`; дополнительную копию для встречи не создавать.
- Все вызовы GigaAM, включая существующие живые методы, проходят через единый механизм допуска с двумя приоритетами.
- При наличии ожидающих живых вызовов новый фрагмент встречи не запускается. Активный native Decode завершается штатно.
- Слот GigaAM захватывать на один фрагмент, освобождать сразу после Decode. Не удерживать его во время декодирования файла, Nemotron или всей встречи.
- Ожидание выполняет текущий обработчик с учётом context; отдельного dispatch-worker нет.
- Постоянная живая нагрузка может надолго отложить встречу. Эту семантику документировать и измерить ожидание.

## 8. Транспорт, ошибки и остановка

- Серверный `MaxRecvMsgSize` — максимум из существующего `MaxSegmentBytes + 1024` и `MEETING_CHUNK_BYTES + 1024`. Дополнительно проверять размер bytes-поля чанка. Старые прикладные лимиты живых сообщений сохраняются.
- Клиентский лимит отправки согласовать с размером чанка и protobuf overhead. Для полного ответа задать серверный `MaxSendMsgSize` и клиентский `MaxCallRecvMsgSize` в пределах `math.MaxInt32`; проверить размер ответа перед отправкой.
- Размер буферов загрузки не растёт с размером исходного файла; учитывать внутренние буферы gRPC и файловой системы. Полный результат и его сериализация требуют RAM, зависящей от числа интервалов и объёма текста.
- Новый метод не наследует 60-секундный timeout живой сессии. Основной deadline задаёт клиент; отдельный необязательный timeout встречи не ограничивает длительность аудио.
- Ошибка `Recv`, несовпадение длины, обрыв соединения, отмена и ошибка pipeline завершают handler с очисткой файлов и слота через `defer`.
- При отмене во время native-вызова слот остаётся занят до фактического возврата из него. Не освобождать слот отдельным callback раньше завершения вычисления.
- Для client-streaming не нужны `InTapHandle`, `stats.End` и отдельные состояния загрузки/вычисления ради допуска: слот охватывает весь stream handler.
- Переполнение диска/занятый слот/технический предел сообщения → `ResourceExhausted`; неверное аудио → `InvalidArgument`; отмена/deadline → соответствующие статусы; ошибка inference → `Internal`; остановка → `Unavailable` для новых встреч.
- Временные ресурсы удаляются при успехе, ошибке и штатной отмене. После SIGKILL defer не работает: остатки чистить при следующем запуске в выделенном каталоге.
- SIGTERM закрывает admission, отменяет активную встречу, ожидает возврата native-вызова и обработчика, затем уничтожает модели. Не вызывать `diar_destroy` параллельно с `push`.
- Согласовать ожидание handlers, server shutdown и Compose grace period. Для зависшего native-вызова окончательное принудительное завершение выполняет supervisor.

## 9. Упаковка контейнера

Новые build-stage:

1. Закреплённый NeMo-Speech.cpp и его submodules; собрать CPU-компонент diarization и C ABI без TTS, HTTP/Riva-сервера и ненужных приложений.
2. Скачать закреплённый checkpoint Nemotron, преобразовать официальным converter в GGUF с явным `--outtype f32`, проверить артефакт и записать manifest с revision/SHA256 и фактическими типами. Валидатор разрешает F16 только для `subpixel_upsample.weight`: этот профиль SDK не означает F32 для всех тензоров и операций.
3. Скомпилировать Go с cgo, заголовками и библиотеками SDK. Проверить runtime-зависимости и rpath совместно с существующим sherpa/ORT.
4. В финальный образ скопировать обе модели, Silero, необходимые библиотеки и лицензии. Python, converter, компиляторы и исходный checkpoint оставить в build-stage.

CPU-образ должен запускаться без CUDA/NVIDIA-драйверов под текущим UID 65532. Выделить доступный для записи временный каталог. Сборочные зависимости NeMo держать отдельно от существующей среды экспортера GigaAM.

GPU-этап: собрать CUDA backend того же SDK, использовать тот же F32 GGUF, проверить совместимость CUDA-библиотек, затем измерить общий пик VRAM на карте до 10 GB. Без успешного замера GPU-поддержку готовой не считать. При явном выборе CUDA не подменять его незаметно CPU.

Суммаризатор не реализуется: новая ручка готовит для него структурированный результат.

## 11. Порядок реализации в ветке diarization

1. Создать `diarization` от актуальной согласованной базы, перенести этот план в ветку.
2. Проверить SDK и F32-конвертацию на коротком аудио в CPU build-stage; закрепить версии и формат артефакта.
3. Собрать CPU-образ с моделью и минимальной cgo-обвязкой, проверить запуск без сети.
4. Добавить client-streaming контракт, приём чанков на диск и admission до первого Recv.
5. Реализовать seekable-декодирование, хранение PCM и сохранение времени.
6. Добавить длинную диаризацию через одну stateful-сессию.
7. Реализовать построение фрагментов и последовательные вызовы общего GigaAM.
8. Добавить приоритет живого ASR, отмену, ошибки и безопасную остановку.
9. Пройти CPU-проверки, замерить полную двухчасовую запись и живую нагрузку.
10. Добавить и проверить GPU-сборку после принятия CPU-результата.

## 12. Критерии готовности

- Полная запись загружается чанками и обрабатывается в одном client-streaming RPC с одним полным ответом; первый и последний фрагменты не потеряны.
- На транспортном стенде передать файл больше 2 GiB без сборки всего файла в RAM; проверить число принятых байтов, содержимое/хеш и отсутствие зависимости размера буфера загрузки от длины файла. Это отдельная проверка транспорта, не обязательный inference на многогигабайтной записи.
- Проверить разные размеры чанков, последний короткий чанк, неверный/повторный/отсутствующий header, пустые и слишком большие чанки, несовпадение длины и обрыв загрузки.
- Паузы не сдвигают интервалы. Номера спикеров сохраняют состояние через окна; новая встреча создаёт новую сессию.
- Пересечения содержат всех обнаруженных спикеров, смешанный текст не дублируется по участникам.
- Каждый ASR-фрагмент укладывается в лимит; проверены длинная речь без пауз, короткие перебивания, начало/конец файла и неполный последний блок.
- На записи дольше горизонта свёртки SDK, включая два часа, сегментация согласована по всей временной шкале.
- Проверены повреждённый файл, пустая речь, занятость, отмена во время загрузки/FFmpeg/Nemotron/GigaAM, нехватка диска и shutdown.
- Проверены malformed protobuf, ошибка первого Recv, отмена и второй одновременный RPC: слот освобождается на всех путях, но не раньше возврата работающего native-вызова.
- Подтверждён приоритет живых вызовов и отсутствие регрессии старых wire-имён, buffered/unbuffered и WebSocket.
- CPU-контейнер работает без сети и CUDA с запечёнными настоящими моделями. Проверены все необходимые динамические библиотеки.
- Для CPU записаны время каждого этапа, RTF, peak RSS, временный диск и задержки живых запросов. Для GPU дополнительно peak VRAM.
- Качество оценивается по ручной разметке реальных встреч: DER с указанными collar/overlap и WER/CER. Отдельно учитывается ошибка назначения спикеров; качество текста не подменяет качество диаризации.
- Численные целевые DER/WER и время обработки определяются по измерениям на пользовательских данных; сейчас таких измерений нет.
