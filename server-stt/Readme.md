# Отправка RTP-аудио в STT: проблема и исправление

В этой папке находится код из предоставленного архива с исправлениями. Это фрагмент сервера, а не самостоятельное приложение. Структура `vks/stt/` сохранена как в архиве; в основном проекте файлы относятся к `internal/vks/stt/`.

## Что было сломано

Раньше отправка работала так:

```text
ReadRTP → SampleBuilder → Ogg-буфер → накопилось 10 000 байт?
                                         нет → снова ReadRTP
                                         да  → очередь → Send → Recv
```

1. **Короткая фраза могла остаться в буфере на всю паузу.** Проверка размера выполнялась только после нового RTP-пакета. Если человек сказал несколько слов и передача прекратилась, например из-за DTX, буфер не отправлялся. Пакеты тишины тоже не решали проблему: порог мог набираться очень долго.
2. **Не было предела ожидания.** 10 000 байт сжатого аудио соответствуют разной длительности. Частота отправки зависела от кодирования и поступления данных. Быстрая речь сама по себе не означает больше RTP-пакетов в секунду.
3. **Хвост терялся при завершении.** Остаток меньше порога не передавался при EOF или ошибке чтения. Повторные ожидания EOF могли дополнительно занять 36 секунд.
4. **Отправка ждала ответ на предыдущий чанк.** Цикл `Send → один Recv` останавливал последующие отправки и предполагал ровно один ответ на каждый чанк.
5. **Ошибки обработчика STT не доходили до производителя.** Обработчик мог завершиться, а производитель после заполнения очереди зависал на отправке в канал.
6. **Маленькие отдельные Ogg-потоки требовали корректной упаковки.** Пересоздание стандартного writer с ненулевым pre-skip могло заставлять декодер повторно отбрасывать начало каждого чанка. В проверенной версии writer его `Close()` для `bytes.Buffer` также не добавлял EOS.

## Что изменено

```text
RTP → SampleBuilder → сборщик Ogg
                          │
                          ├─ истёк предел ожидания аудио
                          ├─ достигнут предел размера
                          └─ EOF / ошибка чтения: передать хвост
                                      ↓
                             ограниченная очередь
                                      ↓
                       один последовательный цикл Send

                       отдельный непрерывный цикл Recv
                                      ↓
                             публикация субтитров
```

### Формирование чанков

`BufferedPacketer.Start()` сохранён и вызывает новый `StartContext(ctx)`.

- По умолчанию непустое аудио передаётся в очередь через **1 секунду от первого ожидающего пакета**. Новые пакеты не переносят этот срок. Порог 10 000 байт может вызвать более раннюю отправку.
- `ReadRTP()` получает обновляемый deadline: ожидание чтения ограничено 50 мс либо ближайшим сроком отправки. Таймаут чтения считается нормальным событием. Поэтому отправка работает и при полном отсутствии следующих пакетов, без отдельной goroutine, меняющей общий буфер.
- При обычном EOF и ошибке чтения доступный хвост сначала извлекается из SampleBuilder и передаётся в очередь. Повторные ожидания EOF удалены.
- Из SampleBuilder извлекаются **все готовые кадры**. Окно ожидания сокращено с 200 до 10 sequence numbers: примерно 200 мс при пакетах по 20 мс. После 100 мс без новых непустых пакетов и перед отправкой по времени выполняется принудительное извлечение доступных полных кадров. Это компромисс в пользу задержки: очень поздний пакет может быть отброшен.
- Пустые чанки и одни заголовки не отправляются. Переданные данные больше не изменяются производителем.
- Ожидание свободного места в очереди ограничено 2 секундами и прерывается отменой контекста.

Это предел ожидания **формирования/передачи в локальную очередь**, а не гарантия получения текста за секунду: планирование goroutine, ожидание очереди, сеть и STT добавляют задержку. При перегрузке код возвращает ошибку, а не обещает доставку бесконечного потока. Отсутствие RTP используется для освобождения буфера; оно не объявляется достоверным концом речи.

### Ogg/Opus

`packeter/opus_ogg.go` формирует отдельный Ogg-поток из полных Opus-пакетов:

- заголовки OpusHead и OpusTags;
- число каналов из согласованного кодека;
- pre-skip = 0: на границе транспортного чанка новый encoder lookahead не добавляется;
- granule position по реальной длительности Opus-пакетов, определяемой из TOC;
- корректные lacing, CRC и флаг EOS последней страницы.

Перекодирования нет. Паузы без пакетов не превращаются в синтетическое PCM-аудио; RTP timestamp gaps не добавляются к числу упакованных аудиосэмплов. Отдельные чанки сохраняют прежнюю модель «один самостоятельный Ogg в VoiceChunk.Segment».

Тест с независимым декодером FFmpeg проверяет, что суммарное количество декодированных сэмплов совпадает с количеством переданных. Это проверка контейнера и отсутствия повторного pre-skip, **не оценка качества распознавания**. Начало независимого Opus-потока посреди речи может требовать контекста для лучшего качества. Переход к непрерывному декодированию на STT, VAD и работа с контекстом требуют реализации сервера STT.

### Обмен со STT и завершение

`transcribe.go` запускает один sender и один receiver. Sender не ждёт транскрипт после каждого чанка; receiver читает все ответы, включая несколько partial/final на один входной чанк. Порядок отправки сохраняется.

- Очередь уменьшена с 14 до 4 чанков.
- Поток открывается с отменяемым контекстом вместо `context.Background()`.
- Ошибка отправки, получения или публикации отменяет RPC и останавливает остальные обработчики этого трека.
- На штатном завершении: передача хвоста → закрытие очереди → досылка очереди → `CloseSend()` → чтение оставшихся ответов.
- На ожидание завершения после закрытия очереди отведено 10 секунд, включая возможный блокирующий `Send`. После `CloseSend` также действует таймаут ожидания финальных ответов.
- EOF от STT до завершения входа считается ошибкой. Отключение комнаты и локальный `Remove()` отменяют активные потоки; локальное отключение SDK не обязано вызывать callback.
- При явной отмене / ошибке STT приоритет имеет остановка; доставки хвоста в уже недоступный RPC не обещается.

Отправка и получение используют обычные правила gRPC: один последовательный writer и один reader могут работать одновременно. Исправление предполагает, что сервер способен читать следующие сообщения без обязательного чередования «запрос — ответ». Реализации STT и `.proto` в архиве нет: этот контракт нужно подтвердить на реальном сервере. Разделение Send/Recv не увеличивает скорость самой модели и не ограничивает её внутреннюю очередь.

## Настройки

```go
packer, err := packeter.NewOpusBufferWithOptions(track, ch, packeter.Options{
    FlushInterval:  time.Second,
    MaxBufferBytes: 10000,
    EnqueueTimeout: 2 * time.Second,
})
```

Нулевые значения выбирают значения по умолчанию; отрицательные отклоняются. `MaxBufferBytes` — порог отправки после добавления целого пакета, а не точный верхний предел размера сообщения. Интервал 1 секунда выбран как начальный для отдельного Ogg на чанк. Уменьшение до 100–250 мс следует проверять на качестве и стоимости конкретного STT.

## Изменённые файлы

- `vks/stt/packeter/packeter.go` — время ожидания, deadlines, извлечение кадров, хвост, отмена и ограничение ожидания очереди.
- `vks/stt/packeter/opus_ogg.go` — упаковка коротких самостоятельных Ogg/Opus-потоков.
- `vks/stt/agent.go` — контексты, координация производителя и RPC, ограниченное завершение.
- `vks/stt/transcribe.go` — независимые Send/Recv и обработка ошибок.
- `*_test.go` и `packeter/testdata/tone.ogg` — регрессионные проверки; звуковой пример синтетический.

`WithParticipant` теперь получает `ctx` и `cancel`, связанные с открытым RPC; вызов в `OnTrack` обновлён. Если основной проект вызывает этот метод из других мест, их нужно обновить аналогично. Отмена дочернего контекста, который не использовался при открытии RPC, не разблокирует его сетевые операции.

## Проверка

Нужны Go 1.23+ и FFmpeg с поддержкой Opus:

```bash
bash server-stt/validation/check.sh
```

Для нестандартного пути Go:

```bash
GO_BIN=/path/to/go bash server-stt/validation/check.sh
```

Скрипт создаёт временный модуль, копирует изменённые компоненты, запускает `go test -race` и `go vet`, затем удаляет стенд. В нём закреплены LiveKit SDK v2.3.1 и Pion WebRTC v3.3.6; это версии для проверки, а не восстановленные зависимости исходного сервера.

В архиве отсутствуют `go.mod`, `.proto`, `gen/proto/stt` и внутренний конфиг. Поэтому `validation/stubs/stt.go` содержит **только заглушку типов для сборки стенда**. Она не реализует сериализацию protobuf, не подключается к STT и намеренно паникует при попытке создать реальный клиент. Заглушка не должна попадать в production вместо исходного generated-кода. HTTP-обработчики и полный сервер этим стендом не собираются.

Проверяются:

- короткая фраза без следующих RTP;
- непрерывный RTP, не отодвигающий отправку;
- хвост при EOF и ошибке чтения;
- отсутствие пустых отправок во время тишины;
- отмена на заполненной очереди и таймаут очереди;
- переупорядоченные пакеты, порог размера и неизменность отправленных буферов;
- длительности Opus, Ogg CRC, EOS и декодирование через FFmpeg без потери сэмплов;
- отправка двух чанков до первого ответа и получение трёх ответов;
- ошибки sender/receiver/publisher, отмена и таймаут final;
- преждевременное закрытие STT и отмена активных контекстов при локальном удалении агента.

Результат проверки: Go 1.23.12, **18 тестов успешно**, `go test -race` и `go vet` завершились без ошибок. Проверка FFmpeg включена и прошла.

Полная интеграционная проверка требует исходного проекта и работающего STT: отдельно нужно измерить задержку текста, качество на границах чанков и поведение сервера под длительной нагрузкой.
